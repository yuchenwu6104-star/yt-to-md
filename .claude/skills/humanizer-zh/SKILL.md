# Humanizer-zh

目標只有四件事：**正確、通順、講者原話、不超譯**。humanizer 是寫作層：先拿順稿與逐字稿核對，再寫出一篇由訪談衍生、有脈絡也有原話的文章，查證痕跡不准出現在正文裡。不要矯枉過正：只修會讓讀者誤判的錯，其餘寫進 audit。

## 權威與原則

- 逐字稿是內容、語意、說話人、數字與覆蓋的 ground truth。外部資料只用來核實專名或補充，不得無解釋地推翻清楚的逐字稿。
- **[references/golden-sample.md](references/golden-sample.md) 是文體標準，優先於任何文字規則**（使用者親手編修的版本）。改稿前先讀一遍，改完拿成品對照它。規則與範本衝突時以範本為準。
- 本檔是流程與發布契約的唯一權威。改稿時依問題載入參考，不預先讀完：AI 腔／翻譯腔讀 [references/ai-writing-patterns.md](references/ai-writing-patterns.md)；`_fb_` 讀 [references/self-authored-voice.md](references/self-authored-voice.md)；歸屬、數字、串接等高風險情況讀 [references/regression-cases.md](references/regression-cases.md)。
- `scripts/final_gate.py` 是機械門檻，通過不代表文章正確或自然，不能取代逐字稿核對與 fresh review。
- 保留原稿不動，輸出到 `_humanized.md`，不另建 `_raw.md`。
- `_yt_` 交來的是**中文全文順稿**（依字幕順序、說話人前綴行、無小標、frontmatter `type: yt_transcript_zh`），不是文章。選材、段落順序、小標、串接由 humanizer 決定，把訪談重新組織成一篇有脈絡的文章；但不加入編輯者第一人稱、心得或新論點（黃金範本裡編輯者零觀點）。
- **紅線是脈絡句 vs 新資訊句。** 脈絡句只重組已有資訊、不宣稱新事實，可以寫而且要多寫：把讀者帶進下一段、指出這段在回應什麼、點出兩件事的關係。範本實例：「股價的位置與這些數字對不上。」「他反駁這個利空的方式，是重新定價。」「錯誤的說法傳得比較快。」「長約一旦成為主軸，毀約就變成一場賽局。」反過來，新增逐字稿沒有的事實、數字、因果、立場或評價就是超譯，禁止；編者按語與免責句見下節。
- 逐字稿查無的整段一律刪除（順稿仍可能夾帶整段幻覺）。
- 最終中文不使用 em dash `—`，零容忍，交付前全文搜尋清除。
- 正確性優先於風格。無法確認時保守措辭或標示待確認，不猜。
- 不修改 watcher、launchd、processed state、正式輸出路徑或憑證，除非使用者明確授權。

## 引述層：預設就是直接引述

講者的論證、判斷、比喻、反問、例子、親身經歷、數字與立場，**預設一律以直接引述呈現**。只有流程性交代、重複口語、與主題無關的枝節，才可以用一句話帶過。優先留能讓讀者認出這個人的句子：轉折、比喻、反問、帶態度的判斷、有節奏的口語。

（設計說明：舊版的引述配額已刪除。配額會誘發湊引述與為達標保留平淡引文，改成正向規則「講者說的就讓講者自己說」。）

講者原話一律用「」承載，不用 `>` 引用塊（與 `/yt` 同一條規則）。

引號內文字代表說話者。可以讓中文自然，但必須保留原意、語氣強度、修辭、比喻、否定、條件、因果與時間順序，以及有意義的口語感；不可磨成公關稿。硬性禁止：虛構引述、把不同講者的話縫成一則引述。逐字稿沒有合適原話時就不引，不得編造。

編輯者只補讀者理解引述所需的最少背景，不在引述前預告一次、引述後再解釋一次。

**編輯者的話要少。** 串接句只回答「誰、對誰、在什麼脈絡下說」，然後讓路；刪不掉的背景才留。判準：整段讀完，編輯者的字如果多過引號內的字，先砍編輯者的，而不是加引述。黃金範本比現行交付版短 37%，引述反而更多。

**對話保留成對話。** 主持人的提問與回答同樣用引述，不要壓成「主持人問到 X，他回答……」。一問一答的張力來自兩人原話並排（實測踩過：`GPU 太多嗎／一個都沒有` 那段曾被壓成單人敘述）。

## 翻譯與編輯層

引號外文字代表編輯者，必須是可直接出版的自然繁體中文：

- 可重組句序、拆句、合句、刪除重複串接、改掉英文詞序與介詞硬譯。
- 英文殘留若是專名可保留；可自然翻譯的普通詞一律翻譯，不留晶晶體。
- 譯文品質差就**整段重譯**，不做局部美容。
- 朗讀測試：中文會這樣說嗎？不會就重寫。
- **白話，不要書面語**：「市場百分之百認為他們現在賺得太多」不是「市場認定公司的獲利高峰難以持續」；「狠得不得了」不是「工作極為勤奮」；「毒品市場」不改寫成「需求極度旺盛的市場」。譯成人講話的樣子，不要升格成分析報告。
- **具體的東西一律留**：人名、機構名、書名、會議名、比喻、例子。查不到全名時保留字幕能確認的部分（例如只留名字不猜姓氏），不要因為「無法查證」就整段捨棄。
- **講者沒講完的句子照留**（「他們早就... 」），不要替他補完整。
- **不解釋術語**：router、flops、prefill、decode、neocloud 直接用，不加註解、不加括號說明。
- **小標少而短，只當路標**：不預告內容也不下結論；沒有合適小標時就不要硬給。

## 正文不得出現查證痕跡

查證是編輯流程，不是正文題材。外部來源、口徑差異、歸屬判斷、未採用的說法預設全部進 `_audit.md`，不得為了展示「有查過」塞回正文。

**判準（一句話）：刪掉這句之後，事實與邏輯有沒有改變？沒有就刪。**

禁止句式，實際被刪掉的反例：

- 「這是原訪談提出的技術方向，並非已經落地的確定預測」
- 「這些數字是 Baker 轉述的市場假設，不是公司財測」
- 「不代表每個資料中心專案都會帶來相同結果」
- 「不是證明 AI 工具必然造成行情失真」
- 同類：「這段話的主體是……」「這是某人的說法／口徑」「公司沒有提供這項財測」「只能證明／不能證明……」「兩者是不同指標」、段尾補一句正反平衡。

有疑慮時，唯一許可的入文形式是最短的 `（補充：……）`；其餘全部進 audit。若正文事實本身錯了，就直接寫正確事實，不重述錯誤、不解說查證過程。

此規則只約束編輯者文字。**講者自己講的限定語、條件、反方、否定照留**，那是引述層。

## 核對要點

**覆蓋**：讀完整逐字稿，不只搜尋關鍵字。順稿是全文，選材必然捨棄枝節，判準是：**重要論點、數據、部位或利益揭露、標的名、機制解釋、反方例證不得遺漏；廣告、寒暄、離題枝節可以捨棄，在 audit 記一筆。** 逐字稿查無的整段刪掉。**逐字稿→文章方向一定要走一遍，不可只核對文章已經寫到的內容**：只做文章→逐字稿方向時，漏掉的段落對讀者完全隱形。不需產出完整對帳表。

**數字**：逐一對帳金額、百分比、倍數、日期、排序、單位與區間，並檢查方向（增加至／增加了、少於／至多、先後／同時）。**英文量級務必換算正確**：million＝百萬、billion＝十億、trillion＝兆；不可把 billion 寫成「億」而少乘十倍。同一數字在標題、內文、引述要一致。

**專名**：人名、公司、產品、地名、技術名詞全部對逐字稿。只有 ASR 可疑、查無、易混淆的才做外部查證。中文或英文 ASR 的同音／近音亂詞依上下文重建（例如英文 `training` 被聽成 `trading`），重建不出就保留原樣並標 `ASR 存疑`，不得美化成另一個猜測。**搜尋結果只證明這個詞存在，不證明講者要說它**（IMEC／in-rack 教訓）；近似拼字要用語境驗證，仍不確定就保留原文或標待回聽。

**歸屬**（兩人以上必做）：先從逐字稿整理 speaker map（身份、固定語氣、被點名方式、可辨識話題），再逐則引述與相鄰串接確認講者，不靠段落位置猜。判定依序用：明確標籤或點名 → 上下輪對話 → 人物專屬經歷與立場 → 最後才是語氣推斷。三層政策：**有訊號證明掛錯就改；完全沒有訊號就保留 `/yt` 原判斷；有訊號證明不是此人但判不出是誰，降級成「節目中提到」而不指名。**

## 流程（四步）

### 1. 備齊來源

找原始草稿、同 basename 的 `_transcript.txt`（沒有才退 frontmatter 的 `youtube_url` 取字幕）。YouTube 網址入口先完整執行 `yt`，保留 stderr 的 `[note]` 警告，再對產出的文章做本流程；不要問要不要做第二步，`$humanizer-zh <URL>` 本身就代表兩段都要完成。**缺來源就不准宣稱「已核對」**，只能明確降級為未核對的文字潤飾。記下原稿與輸出路徑。

### 2. 先核對，再寫成文章

- **核對順稿**：逐段對逐字稿，抓意思錯、抓幻覺（順稿裡字幕查無的內容一律刪）、數字量級與單位、專名、說話人歸屬。**術語與專名有疑問就查證，因為字幕本身可能就是錯的。**
- **寫作**：決定要講哪幾條線、順序怎麼排、小標怎麼下、哪些原話進「」。講者的論證、比喻、反問、判斷、經歷一律還原成直接引述，串接只寫脈絡句。
- 自然繁中：譯文品質差就整段重譯。
- 清掉舞台指示、空泛總結、預告後重講、引述前後同義重述、em dash。

### 3. 冷讀一遍

關掉逐字稿，當一般讀者從頭讀完，抓：邏輯斷裂與因果跳躍、代詞失指、標題與內容不符、贅句與重複、未看過影片的人能不能分辨誰說了什麼。對每段跑刪句測試（見上節判準），命中就刪或移入 audit。

### 4. Fresh review ＋ gate ＋ 上傳

**必須另派一個沒參與改稿的新 agent**，不能只讀 audit，也不能由 producer 自審或預填結論。fresh reviewer 獨立重跑第 2、3 步的判斷：讀完整逐字稿做朗讀式翻譯與正確性檢查，再關掉逐字稿冷讀，並自己跑刪句測試。必改項退回修正、更新文章與 audit；涉及引述、歸屬、數字或新增內容的修正要回逐字稿再核對。最後跑 `final_gate.py`，**零 [硬性] 才能交付或上傳**；[候選] 仍需逐筆人工判定，不因程式沒擋就忽略。

## Audit 契約

每篇完成稿需有同名 `_audit.md`，章節標題固定用 `## 1.` `## 2.` `## 3.`。Audit 是給使用者看的證據，不是自證儀式；記錄實際判斷與依據，不寫「已確認」「看起來正確」這類無來源自評，不留 `TODO`、待盲審等未完成字樣。

```
## 1. 改了什麼
重要修正逐條，附逐字稿行號或時間碼。涵蓋漏補、意思錯、數字、專名、歸屬。純格式修整合併成一條。

## 2. 查過但沒寫進正文的
外部查證結果、口徑差異、未採用的說法、ASR 存疑、未能查證而保留原樣的專名。

## 3. 覆蓋與遺留
逐字稿有但成品捨棄的內容（附理由）、fresh reviewer 的必改項與處理結果、final_gate 結果。
開頭先寫一行掃描範圍與筆數（例：「逐字稿 2064 行讀畢；引述 20 則逐則回對，4 則改動」），
讓「查過沒問題」與「沒查」可以區分。只要一行，不要展開成逐則清單。
```

## 輸入路由

- **本機 `_yt_` 路徑**：視同完整 production 工作，不因輸入是路徑而降級；仍要改稿、audit、fresh review、gate、upload。
- **批次監督模式**（多個 Vault 路徑＋要求派 agent）：root 負責盤點、指派、驗收、gate 與上傳，不親自重寫每篇；每篇分開一位 producer 與一位 fresh reviewer，角色不可兼任，同一 reviewer 不在同一 context 連審多篇；字幕下載錯開，不並行多個 MLX Whisper。
- **`_fb_` 或作者自寫文**：可更積極恢復個性、節奏與觀點，但不新增事實；另讀 voice 參考。
- **純文字或其他檔案**：先確認來源與輸出位置；貼文直接回傳改寫文字，檔案預設另存新檔保留原檔。沒有來源就不假裝核對。

## 輸出與發布

原稿保留不動；完成稿同目錄同 basename 加 `_humanized.md`；逐字稿 `_transcript.txt`；稽核 `_audit.md`。完成稿正文不得混入 audit、流程說明、分數或「以下是修改後版本」等聊天語句。

```bash
/Users/slking/Documents/訪談摘要/.venv/bin/python \
  .claude/skills/humanizer-zh/scripts/final_gate.py \
  /absolute/path/to/article_humanized.md
```

`final_gate.py` 與引述有關的 [硬性] 只有一條：引號內 CJK 字數佔全文 CJK 字數不足 0.45（黃金範本 63%）。撞到代表全文被磨成第三人稱摘要，**先砍編輯者的話，其次才是還原引述**。另有 [候選] 佔比不足 0.60 的提示。門檻不要改。

`scripts/upload_hackmd.py` 僅在以下全部成立時執行：三個檔齊全、fresh review 必改項已處理、final gate 零 [硬性]、使用者沒有禁止上傳或要求 dry run。依檔名傳 tag：`_yt_` → `YT訪談摘錄`、`_fb_` → `FB文章`、`_invest_` 或 `_epub_` → `投資筆記`。預設個人空間、`readPermission=guest`。要求原位更新時更新既有筆記，不建立重複筆記。不得輸出 token 或 `.env` 內容。`_yt_` 保留頁尾「本文根據 YouTube 影片內容由 AI 整理生成，僅供參考。」

## 交付回報

回報可驗證事實，不自評分數：產出檔案路徑、重要修正（漏補／歸屬／數字／專名／翻譯）、fresh review 必改項與處理結果、final gate 結果、HackMD URL（dry run 則明說未上傳）。
