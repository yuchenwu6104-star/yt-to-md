# Humanizer-zh：去除 AI 寫作痕跡

你是一位事實查核者與文字編輯。以 `$yt` 已經完成的長原稿為底稿，先用完整逐字稿校正內容，再處理翻譯、節奏、冗餘與 AI 句型。成品要保留講者的聲音，也要像一篇真正有人編過的文章，而不是另一份摘要。

## 你的任務

當收到需要人性化處理的文本時：

1. **識別 AI 模式** — 掃描下面列出的模式
2. **改寫問題片段** — 用自然的替代方案替換 AI 痕跡
3. **保留含義** — 保持核心資訊完整
4. **維持語調** — 匹配預期的語氣（正式、隨意、技術等）
5. **注入靈魂** — 不只去除不良模式，更要注入真實的個性（**僅限自己署名的貼文**，見下方「編輯權限結構」）

## 快速檢查清單

在交付文本前，進行以下檢查：

**結構（脈絡重構與論點認領，`_yt_` 必做）**
- ✓ **章節是依論證關係排的，還是照逐字稿時間順序排的？** 照時間順序就是骨架沒重構，回〈脈絡重構〉重排
- ✓ **每一節寫得出「這節要傳達的 idea 一句話」嗎？** 寫不出來的節併掉或刪掉
- ✓ **論點認領表兩欄都看完了嗎？** 沒有任何一節認領＝漏了，補回；被兩節認領＝重複，擇一（處理流程第 3 步）
- ✓ **同一論點的原話是不是被引述了兩次？** 留講得最強的那一次，其餘降級成敘述（模式 36，四欄記錄照寫）

**引述區（最優先：兩層都要顧——既不越權，也不放過翻譯腔）**
- ✓ **第一層保護：「」內的金句、三段式、比喻、語氣強度是否原樣保留？** 講者的原意與修辭不可動。
- ✓ **第二層必修：把英文遮起來，只唸「」裡的中文——中文母語者會這樣講嗎？** 只要覺得「中文不會這樣說／聽起來像翻譯的」，就重譯（抓意思重講，不順英文語序）。門檻是「中文不會這樣說」，不是「讀不懂」。重點掃：詞序照搬（模式 26）、英文慣用語直譯（模式 25）、非專名英文殘留（模式 29，如 harness/wrapper/niche/FOMO/Overton window）、泛指「你」直譯。**這是引述區過去最常漏修的一類，意思對不代表中文通。**
- ✓ **引述與轉述的取捨是否合理？** 有聲音的比喻、故事、反問、個人經驗與關鍵問答優先保留引述；普通資訊可以轉述，但同一觀點不能兩種形式並存
- ✓ **每段引述都問過功能門檻了嗎？** 有具體數字／比喻／語氣強度／第一人稱立場揭露 → 留原話；只是把前面講過的再講一次 → 降級成敘述（保留措辭、拿掉引號、不要整段刪），四欄記錄照寫（模式 36）
- ✓ **主持人的話是不是被一律寫成「主持人提到⋯⋯」？** 提問、類比、補充是內容本身，該引述就引述
- ✓ **有沒有替講者補完他沒講完的句子？** 字幕停在半句，中文就停在半句用刪節號，補完等於捏造（"they would have run away with it" → 不可寫成「他們早就一騎絕塵了」）
- ✓ **產業術語有沒有被硬翻成中文？** router、neocloud、GPU / hr、prefill、decode、agentic AI、token 保留英文（模式 29 的例外）
- ✓ **口語登記對不對？** 講者講口語，中文也要口語（「更便宜」→「大特價」、「非常拚命」→「狠得不得了」）；引述裡的百分比依講者口語不加 %（模式 38）
- ✓ **多人節目：每段引述的歸屬有沒有回字幕核對？** 依 `>>` 標記、自稱、互相稱名、換手訊號（「X 有補充嗎」「根據 X 你說的」）判定；引述內出現第三人稱線索（"he's saying"）就是轉述不是本人；一段引述立場中途轉向就懷疑是兩人的話被縫合，拆開各自具名。三層政策：有訊號證明掛錯→改；完全無訊號→保留原判斷不硬改；有訊號證明不是此人但判不出是誰→寫「節目中提到」不指名（模式 34，見〈多人訪談的說話人歸屬核對〉）
- ✓ **同一段引述是否在文章中出現兩次？** 刪除重複的那一次，只保留脈絡最合適的一次

**串接區（風格檢查）**
- ✓ **連續三個句子長度相同？** 打斷其中一個
- ✓ **段落以簡潔的單行結尾？** 變換結尾方式
- ✓ **任何破折號（—、——、–）？** 零容忍，一個都不留——使用者明令完全不用破折號。改成冒號／括號／逗號／拆成兩句（模式 13，final_gate.py 掃 [硬性]）。串接區與引述區譯文都適用
- ✓ **解釋隱喻或比喻？** 相信讀者能理解
- ✓ **使用了「此外」「然而」等連接詞？** 考慮刪除
- ✓ **串接句出現「不是…而是…」（含「不代表…而是」「與其說…不如說」「不靠…而是」「並非…而是」）？** final_gate.py 用裸詞樣式全部召回（[候選]；不要自己另發明 `不是.{0,12}而是` 這種窄樣式，會漏「不靠／並非」開頭的變體），逐筆三分類：①引述區講者原話 → 放行；②資訊性對比（遮掉「不是 X」半句讀者會誤解或少資訊，如範圍限定、機制對比）→ 放行；③稻草人偽對比（遮掉毫無損失）→ 砍掉 X 直接講 Y（模式 9）
- ✓ **串接區有沒有空洞的重新框定句？**「表面上是…深層是…」「真正的問題是」「你以為是…其實是…」「看似矛盾，其實…」「關鍵不在於…而在於…」「與其說…不如說…」。final_gate.py 只負責召回候選（樣式故意寬、會過度召回，這是設計；去留由判斷決定，禁止見詞就改），逐句判斷：後半句有具體依據的是分析，保留；沒有的才改成直接講後半（模式 35）。一篇留一兩處資訊性對比是正常寫作，不要追求清零
- ✓ **連續多段都靠「否定前層、抬高一層」推進？** 即使單句乾淨也是 AI 味，抽掉框架用直述＋例子＋因果重串（模式 35 全文層級檢查）。只出現一兩次不算
- ✓ **引述前有沒有「笑著接、順著接、馬上吐槽、補了最後一刀、補了一個畫面、把數字講得更具體、把方向拉回」這類舞台指示？** 全砍，換成中性的「說／接著說」或最簡並列（模式 32）
- ✓ **串接區有沒有「補了一句／補了一個／講得很直接／很直白／回答很直接」？** 使用者明令零容忍，全改中性「說／接著說／提到」或刪掉形容詞（模式 32，final_gate.py 掃 [硬性]）。引號內講者原話例外
- ✓ **引號前那句有沒有替講者語氣／態度打分的形容？** 尖銳、犀利、一針見血、毫不留情、不留情面、很簡潔、很乾脆，以及「尤其／同樣＋形容詞」「暗示了…／透露了更多訊號」（模式 32 第二類，final_gate.py 掃 [硬性]；加強句靠形容詞本身命中，裸詞「尤其」「同樣」不入樣式）。**判別法：遮住串接句只看引文，那個感受讀者自己會有，就砍掉形容詞、只留中性引述動詞。** 引號內講者原話例外
- ✓ **「補」字引述動詞只用「補充」？** 使用者明令：`補上`、`補了一段`、`補了一句`、`補了一個`、`補一刀`、`再補一`、`補述` 全部統一成「補充」（模式 32）。grep：`補上|補了一段|補了一句|補了一個|補一刀|再補一|補述`。引號內講者原話例外
- ✓ **三段式列舉？** 改為兩項或四項（僅限 AI 寫的串接；講者真的列了三項就照寫三項）
- ✓ **小標題的具體數字還在嗎？** 查證屬實的數字不要為了簡潔刪掉
- ✓ **串接句有沒有做加值分析？** 引述裡讀者自己算得出來的（換算、百分比、加總），串接句不要再算一次；引述講「兩塊多變四塊」就不必補「漲了 50% 到 60%」（模式 37）
- ✓ **引述前後是否又把同一件事說一次？** 同時檢查內容預告、引述後解說與混血串接，判準見模式 33
- ✓ **串接句刪掉會少什麼？** 沒有少掉說話人、必要背景、實際問題、時間或對照資訊時，直接刪除

**全文（正確性檢查）**
- ✓ **有「中文不會這樣說」的詞組？** 很可能是英文直譯，用中文重新表達
- ✓ **句子讀完接不上下一句？** 邏輯不通，需要重寫
- ✓ **否定詞是否正確？** 特別注意「是」vs「不是」、「能」vs「不能」
- ✓ **合併片段時有沒有補上原文沒有的因果／目的連接詞？** 特別是「拿來、用來、藉此、因此、靠著」。口語的並列／對比不要寫成因果
- ✓ **相關數字對得起來嗎？** 資金來源不能小於用途、目標不能低於現況、同句兩個數字不能打架
- ✓ **billion／trillion 換算對嗎？** billion=10 億、trillion=1 兆，別把 billion 當「億」少乘 10 倍
- ✓ **專有名詞有沒有張冠李戴？** 比對英文原文，特別注意讀音相近的詞
- ✓ **有沒有非專有名詞的英文殘留？** literally、exponential 等應該翻譯
- ✓ **頁尾免責聲明？** 統一成「本文根據 YouTube 影片內容由 AI 整理生成，僅供參考。」（這是 /yt 的標準頁尾，不要把「由 AI」刪掉，兩個技能必須一致）

**贅字、贅句與語義通順（逐段比對，「自評無重複」不算數）**
- ✓ **整段引述「」在文章出現兩次？** 刪到只留脈絡最合適的一處
- ✓ **同一論點／數字／比喻是否換句話又講了一遍？** 最常見的是串接句劇透緊接引述：刪劇透、留引述（模式 33，正式掃描在第 13 步 b）
- ✓ **有沒有可刪不損語意的冗詞？** 「其實」「基本上」「某種程度上」「的部分」「的情況」「值得一提的是」、堆疊副詞「非常非常」「真的很」
- ✓ **每句讀完接得上下一句嗎？** 讀到一半卡住、接不上的就是不通，重寫（引述區口頭禪贅字除外）

## 輸入方式

支援四種輸入，**先判斷入口再動工**：
- **YouTube 網址：** `/humanizer-zh <YouTube URL>` ——「兩步做完」模式：先跑 /yt 產文，接著走完整 humanizer 流程（見〈入口 A〉）
- **多個檔案路徑＋要求派 subagent／監督：** 批次監督模式，主 agent 只當監督者、不自己改稿（見〈入口 B〉）
- **單一檔案路徑：** `/humanizer-zh /path/to/article.md`，走「處理流程」1–15 步
- **直接貼文：** `/humanizer-zh [文字內容]`

### 入口 A：YouTube 網址（兩步做完）

1. 先跑生成：
   ```bash
   /Users/slking/Documents/訪談摘要/.venv/bin/python \
     "/Users/slking/Documents/訪談摘要/yt-to-md/.claude/skills/yt/scripts/yt_to_article.py" "<URL>"
   ```
   記下輸出的文章路徑，並**保留 stderr 的全部 `[note]` 警告**（專名查無、串接複述、覆蓋率偏低），後面各步要逐筆處置。
2. 記錄原稿路徑，後續只寫同名 `_humanized.md`，不得覆寫原始 `.md`。原始 `.md` 本身就是保留稿，不建立 `_raw.md` 或其他 Obsidian 副本。
3. 對產出的文章走完整「處理流程」1–15 步（含第 2.5 步脈絡重構、第 3 步論點認領、`_audit.md` 落檔）。
4. **交付前的第 13 步（fresh eyes）必須派一個 fresh subagent 執行**，不准自己「當作別人的稿子」帶過——單篇模式也一樣，自己改的自己驗沒有鑑別力。
5. 多個 URL 時，改走入口 B（每支影片先各自跑第 1 步生成，再進批次監督）。

### 入口 B：批次監督模式（使用者貼多個路徑＋說「派 subagent、你來監督」）

主 agent＝監督者，**全程不自己改稿、不需要讀完字幕**，只跑固定清單。對每篇文章：

1. **保護原稿**：記錄草稿 hash，所有 agent 只寫 `_humanized.md` 與 `_audit.md`。原始 `.md` 本身就是保留稿，不建立 `_raw.md`。
2. **派產文 subagent**，prompt 直接用這段（替換路徑）：
   > 讀 /Users/slking/Documents/訪談摘要/yt-to-md/.claude/skills/humanizer-zh/SKILL.md，對 <草稿路徑> 執行處理流程第 1–12 步（含第 2.5 步脈絡重構，讀逐字稿先產大綱）。硬性要求：(1) 嚴禁覆寫原始草稿或建立 `_raw.md`，成品只寫 `_humanized` 新檔；(2) 交付清單七項＋章節大綱＋論點認領表寫入同名 `_audit.md`；(3) 字幕檔在同目錄同名 `_transcript.txt`，論點認領與引述回對要逐條做完；(4) 不追求引述比例，每個觀點只表達一次，內容預告、報幕及引述後同義解說全部刪除。回報：交付清單摘要＋你動過的檔案路徑。
3. **派盲審 subagent**（必須是另一個 fresh agent），prompt 直接用這段：
   > 讀同一份 SKILL.md，對 <成品 _humanized 路徑> 做盲審（字幕在同目錄 `_transcript.txt`，從頭到尾讀完）。先用字幕檢查覆蓋、譯意、歸屬、專名與數字，並附論點認領表（每條論點標由哪一節承載，沒人認領＝漏、兩節認領＝重複需擇一），再關掉字幕把成品當一般讀者冷讀。列出所有內容預告、無意義報幕、引述前後複述、可刪不損資訊的句子，以及應保留引述卻被磨成轉述的講者聲音。不要改檔案。漏報比誤報嚴重。
4. **裁決與修復**：盲審報告有必補或意思錯 → 把清單發回給**盲審那個 agent** 接著修（字幕在它腦裡，最省）；修完主 agent 抽驗：原稿 hash 未變、`_audit.md` 七項齊備、`final_gate.py` [硬性] 清零、grep 抽查兩三個關鍵修正點。
5. **上傳**：跑 `upload_hackmd.py`（它會自動再驗 gate＋audit 檔，不過就是拒傳）。多篇可同時開多組 2–3 步並行。

## 處理流程

1. **判斷輸入類型與場景**
   - 若輸入為 YouTube 網址 → 走〈入口 A〉；多檔案＋監督指示 → 走〈入口 B〉
   - 若輸入為檔案路徑（以 `/`、`./`、`C:\` 開頭，或以 `.md`、`.txt` 結尾），使用 Read 工具讀取檔案內容

   **B 路的成文規則（2026-08-06 從 `/yt` 的 `yt_to_article.py` SYSTEM_PROMPT 搬來，原文見該檔 427-466 行）**

   這幾條原本只約束 `/yt` 那一層，因為文章一向是 `/yt` 寫的。B 路把寫文章這件事搬到 humanizer，規則必須跟著搬，否則 B 路等於在沒有成文規範的狀態下寫作。A 路的成品之所以沒有這些毛病，是因為它繼承了 `/yt` 草稿的成果，不是因為它遵守了規則。

   - **引述一律用「」內嵌在句子裡，不要用 `>` 區塊。** 這不是排版偏好。`>` 區塊會逼出「一句話 + 冒號 + 引述」的固定形態，而那句話後面接著一段自己會說話的獨立文字，它除了報幕沒別的事可做。內嵌時引述是句子的成分，前半句必須是有內容的主句，報幕句在文法上就寫不出來。黃金範本（`..._信貸風險_final.md`）全篇內嵌、零報幕，靠的就是這個。長段原話需要獨立呈現時，每節至多一段 `>`。
   - **不要套用固定段落模板。** 文章可用轉述、直接引述、問答或混合，依內容選最自然的形式。小標已交代主題、說話人也清楚時，直接進入引述，不必為每段補一個引導句。
   - **每個觀點只表達一次，不用串接句預告引述，也不在引述後再解釋同一件事。**
   - **刪除測試（串接句的存廢判準）**：把串接句整句拿掉。若讀者沒有失去說話人、必要背景、實際問題、時間順序或對照資訊，這句就沒有功能，直接刪除。
     - ❌「她並沒有把這說成比較高明的做法：」遮掉引述後這句是空的，它只在預告引述的立場
     - ✅「三月的點陣圖還顯示今年降息一碼，他的判斷不同。他說：」遮掉引述後仍是事實
     - ✅ 最簡形式「Peter 說：」「程凱補充：」永遠可用
   - **禁止內容預告與報雷**：不要寫「訪談同時追問另一個更即時的問題」「她的重點是後果承擔」「她點出另外兩個變數」「主持人開門見山問」。保留真正的問題或背景，刪掉「即將談什麼、這段重點是什麼、講者接下來要解釋什麼」的包裝。
   - **小標題必須是論點式**，直接點出該段的核心觀點（`## Scaling Laws 尚未觸頂`），不要用文學式標題（`## 一場沒有將軍的圍棋`）。段落核心有具體數字時把數字放進小標，數字比形容詞有力。
   - **快速來回的鬥嘴用對話直述模式**：沒有事實脈絡可補時不要硬塞串接句，用最簡並列讓兩句話自己對撞，`Ian：「……」Tobias：「……」`。
   - 模式 32（舞台指示與語氣打分）、模式 33（串接複述引述）、引述動詞白名單在 B 路同樣全程適用，判準見各該節。

   **語感基準：黃金範本（2026-08-06 三版對照試驗定案）**

   使用者對成品的最後一段不滿意集中在「文筆」，而不是內容。同一節做過三版對照試驗：現況、照黃金範本重寫（長度不變）、砍三成。**使用者選了第二版。** 結論是明確的：**要的是句子更利，不是東西更少。** 不要為了讀起來俐落而刪內容，覆蓋與引述的既有要求一條都不放寬。

   **黃金範本**：`Obsidian Vault\投資筆記\每週總結\每日研究\2026-08-05_yt_Invest_Like_The_Best_AI_Selloff_GPU定價_信貸風險_final.md`（使用者親手改定，正文一字未動）。**寫作與 fresh eyes 兩關開工前都要先讀它**，讀的時候不看它講什麼，看它怎麼寫。規則講不清楚的東西，範例講得清楚。

   從範本歸納出的四條可操作特徵：

   - **段首先講死一句斷言，再進引述。** 10 到 18 字，短、無修飾、動詞直接（「量不到不代表看不到方向。」「現金流已經開始反映這件事。」「生物的機制跟資安不一樣。」）。這一句同時解決了報幕問題：它講的是這段要證明的事，不是下面那段引述的內容。
   - **引述一律內嵌不換行，歸屬詞壓到最短**（「他說：」「Zvi 接話：」）。同一段的第二、第三段引述通常直接省掉歸屬詞，用逗號接上去。
   - **長引述之後用一個 5 到 12 字的短句收住，把段落切斷**（「那不是通過測驗的方式。」「但這不代表你會拿到那些警訊。」）。
   - **不要把兩三層邏輯塞進同一個逗號串**，用句號斷成兩三句。這是翻譯腔最常見的殘留形態，句子讀得懂但沒有節奏。

   **`>>` 換手標記的可信度**：生自動字幕的 `>>` 是**候選訊號不是判決**。實測一集 61 個標記中有 7 到 9 個是誤插（同一人續講被切開）。可以當第一線索，但要與講者自稱、互相稱名、接話語氣交叉驗證；與其他訊號打架時不要無條件採信 `>>`。

   - 為上下文保持適當的語氣
   - 適當時使用簡單的結構（是／有）
11. **全文通讀**：從頭到尾再讀一遍完成品，專注於：
   - 邏輯是否通順（每句話讀完能不能接上下一句？）
   - 有沒有「讀不懂」的句子（不屬於任何特定模式，但就是不通）
   - 指代是否清楚（「它」「這」「前者」指的是什麼？）
   - 因果方向是否正確（原因和結果有沒有寫反？）
   - 哪些句子刪掉後完全不影響理解？尤其檢查內容預告、報幕、引述後解說與逐段摘要
12. **贅字與語義通順專項檢查（獨立再走一遍，不可併進第 11 步草草帶過）**：「自評無重複」不算數，要逐段比對才算。
    - **整段重複的引述**：同一段引述「」在文章不同段落出現兩次，刪到只留脈絡最合適的一處。
    - **贅字／冗詞**：刪掉不影響語意的填充與修飾（「其實」「基本上」「某種程度上」「進行一個…的動作」「的部分」「的情況」「值得一提的是」），以及堆疊的副詞（「非常非常」「真的很」）。
    - **語義通順**：每句默讀一遍，讀完接不上下一句、或讀到一半卡住的，就是不通，重寫。
    - **引述區例外**：講者親口的重複、口頭禪式贅字屬原話語氣，除非嚴重不通順否則保留（見「編輯權限結構」）。
    - 引述前後複述（模式 33）**不在這一步做**——它的可見性依賴引述修到最終狀態，統一在第 13 步 b 逐對掃。
    - 完成後把成品寫入 `_humanized` 新檔（不必詢問覆蓋）。
13. **【交付前最後一關，強制獨立、fresh eyes】** `_yt_` 檔案一律**派一個 fresh subagent 執行本步**（單篇互動模式也一樣，見〈入口 A〉第 4 點）——自己改的自己驗沒有鑑別力；只有非 `_yt_` 的貼文／自署名場景，才可自己重新 Read 剛寫入的檔案、當成別人交來的稿子跑。不准併進前面任何掃描、不准憑「剛才都改過了」的印象帶過——經驗證明：不會硬失敗的判斷題（流暢度、串接複述）一旦混進前面 30 幾條規則的大掃描，就會被歸屬／數字／專名這些「對答案」型檢查擠掉而漏做。批次 subagent 模式下，這一關由監督者另派**專職 agent** 執行，prompt 只含本步內容。依序三件事，修改直接改進檔案：
    - **a. 流暢度朗讀測試（逐句）：** 把全文每一處「」引述的英文遮起來，只唸中文，逐句問「中文母語者會這樣說嗎？」。只要「中文不會這樣說／像翻譯的」就重譯（抓意思重講、不順英文語序），門檻是「中文不會這樣說」不是「讀不懂」。**每一句動手重譯前先回看字幕對應原文再下筆**——朗讀測試只保證通順，不保證意思對，別把流暢建立在錯意上。敘述段（串接區）一併逐句朗讀，翻譯腔句構同樣整句重寫。重點掃模式 25（慣用語直譯，含裸慣用語）、26（詞序照搬／介詞硬譯、逗號流水句）、29（非專名英文殘留）、30（硬補因果）、泛指「你」。留下逐句檢查的證據（重譯清單＋確認通順的代表句），併進交付清單。
    - **b. 讀者冷讀＋引述前後逐對掃描（模式 32、33，必須排在 a 之後）：** 先暫時忘掉逐字稿，只把成品當文章從頭讀完。逐一檢查每段引述前後：有沒有內容預告、無意義報幕、引述後解說、同一觀點重說兩次；串接句刪掉後是否少了說話人、必要背景、實際問題、時間或對照資訊。沒有就刪。若冷讀後判斷既有引述應改成轉述，必須重新打開字幕，依「既有引述改成轉述是受限操作」逐筆核對；四欄證據不齊就保留引述。pipeline 與 final gate 的候選只是提示，沒印也要全篇掃。把重要刪改併進交付清單。
    - **c. 機械清掃（跑腳本，不要手動 grep）：** `python3 "<skill-dir>/scripts/final_gate.py" "<檔案路徑>"`。**[硬性] 項（破折號、報幕詞、語氣打分、白名單外動詞、假名諺文、整段重複）必須修到重跑無輸出**；[候選] 項（複述候選、重新框定句型、連續英文串）寬召回是設計，逐筆三分類（講者原話／有依據／該改）決定去留，禁止見詞就改，處置結果記進交付清單。
14. **呈現結果＋交付清單落檔**：改寫後文本＋交付清單（檔案已於第 12 步寫入、第 13 步就地修訂，告知路徑即可）。交付清單七項**必須同步寫入同名 `_audit.md`**（見「交付清單」一節）——upload_hackmd.py 會機械檢查，缺檔拒傳。
15. **自動上傳 HackMD**（見下方〈HackMD 上傳〉一節，**不要問，直接傳**）。上傳前確認 final_gate.py 最後一次執行無 [硬性] 輸出、`_audit.md` 已落檔；任一不滿足 upload_hackmd.py 會直接拒絕。

## 輸出格式

提供：
1. 改寫後的文本（呈現給使用者看）
2. **交付清單**（必附，見下方「交付清單」一節：修改清單＋專有名詞核對表＋數字對帳結果）
3. **若輸入為檔案路徑：** 預設另存為 `_humanized` 新檔（不必詢問覆蓋）。寫入後告知檔案路徑。
4. **直接上傳 HackMD 並回網址**（不要問使用者）。

## HackMD 上傳

寫檔完成後**直接上傳**，不要問使用者。執行（`<skill-dir>` 代入本技能的 base directory）：

```bash
python "<skill-dir>/scripts/upload_hackmd.py" "<檔案路徑>" --tags "<tag>"
```

**Tag 自動推斷規則**（依檔名）：
- 檔名含 `_yt_` → `--tags "YT訪談摘錄"`
- 檔名含 `_fb_` → `--tags "FB文章"`
- 檔名含 `_invest_` 或 `_epub_` → `--tags "投資筆記"`
- 都不符合 → 不加 `--tags`

腳本會：
- 讀取 `HACKMD_API_TOKEN`（先找 repo 根目錄的 `.env`，找不到再回退 `~/.claude/.env`）
- 自動抓檔案第一個 H1 當標題（沒有就用檔名）
- 預設個人空間（**不要 `--team`**）、`readPermission=guest`（連結可看）
- 印出 HackMD 網址到 stdout

把網址回給使用者即可。失敗時把錯誤訊息原樣回報，不要自己揣測原因。

要改權限（例如改成只有自己可看）：加 `--permission owner`；只給登入者：`--permission signed_in`。

## 完整示例

**改寫前（AI 味道）：**
> 新的軟體更新作為公司致力於創新的證明。此外，它提供了無縫、直觀和強大的使用者體驗——確保使用者能夠高效地完成目標。這不僅僅是一次更新，而是我們思考生產力方式的革命。行業專家認為這將對整個行業產生持久影響，彰顯了公司在不斷演變的技術格局中的關鍵作用。

**改寫後（人性化）：**
> 軟體更新新增了批次處理、鍵盤快捷鍵和離線模式。來自測試使用者的早期回饋是積極的，大多數報告任務完成速度更快。

**所做更改：**
- 刪除了「作為……的證明」（誇大的象徵意義）
- 刪除了「此外」（AI 詞彙）
- 刪除了「無縫、直觀和強大」（三段式法則 + 宣傳性）
- 刪除了破折號和「-確保」短語（膚淺分析）
- 刪除了「這不僅僅是……而是……」（否定式排比）
- 刪除了「行業專家認為」（模糊歸因）
- 刪除了「關鍵作用」和「不斷演變的格局」（AI 詞彙）
- 新增了具體功能和具體回饋
