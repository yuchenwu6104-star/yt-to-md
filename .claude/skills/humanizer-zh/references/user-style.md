# User-Style 格式標準(SLK 專屬)

> 觸發條件:執行 `humanizer-zh` 寫最終交付稿時必須先讀,跟 `golden-sample.md` 同一個優先級。

user 親手編修過的範例(2026-08-08 Hard Fork 白宮框架,檔名 `2026-08-08_yt_The_Verge_What_s_behind_the_Google_AI_audit_humanized.md`)是 user 給的格式參考。User 2026-08-09 明確說明:user-style 是 best practice 但**不是模仿標竿**,humanizer 的判斷基準是「這段話對讀者最好」,不是「對標任何人」。

## 必備結構(漏一條 user 會退件)

1. **YAML frontmatter**:
   ```yaml
   ---
   type: yt_article
   date: YYYY-MM-DD
   source: YouTube
   youtube_url: <URL>
   channel: "<頻道名>"
   video_title: "<原始標題>"
   tags: [...]
   ---
   ```
   - `type: yt_article`(從 `yt_triage` 改寫後變 article)
   - tags 格式 user 還沒選(中文 vs 英文),先混用不阻擋

2. **大標題**:`#` 一個(全文只有一個),`##` 多個小節
   - 大標題要有「問題 + 結論」或「議題 + 轉折」的味道,不要純描述
   - 範例:`# 白宮把前沿模型的規則定好了,然後決定不給你看`(議題 + 反轉)

3. **原始影片區塊**(大標題正下方):
   ```markdown
   > 原始影片:[<標題>](<URL>) | <頻道名> | YYYY-MM-DD
   ```

4. **全形標點優先**:
   - 中文內用 `,。?!;:()「」`(全形)
   - 數字內的 `1,200` 模式保留半形(千分位)
   - URL / 代碼 / 英文引用保留 ASCII

5. **引述**:
   - 優先用 `> ` blockquote 區隔(跟 user 範例一致)
   - 講者原話用「」承載
   - 不要寫 `Friedberg 認為」「Brad 認為」這類「認為」flag 詞(會被 final_gate 抓到)

6. **結尾頁尾**:
   ```markdown
   *本文根據 YouTube 影片內容由 AI 整理生成,僅供參考。*
   ```
   - `_yt_` 系列必加
   - `_fb_` / `_invest_` 不加

## 寫作時的判斷習慣(從 2026-08-09 對話整理)

- **開頭要有頂層 takeaway**:兩到三句話抽出整集的核心 insight / 轉折,不要只寫「Brad 是誰、本集分四塊」這類寒暄
- **小節標題要有結論**:用「問題 + 結論」結構,不要純描述(`「Airtable 為什麼會這樣」` 比 `「Airtable 賣給 Bending Spoons:12.8 億對 117 億」` 好)
- **刪掉舞台指示詞**:`「把鏡頭轉向」「順勢把話往...拉」「他同時點出」這類鏡頭/動作詞 final_gate 會 [硬性] 抓到
- **翻譯口語化**:遇到 podcast 口語就照白話翻,不要翻成書面語
- **早收尾**:不要硬塞到最後一段,留讀者空間
- **「認為」、「透過」、「進行」** 這些是 AI 痕跡詞(ai-writing-patterns.md 也有),盡量不用

## 已知 user-style 但 user 還沒明示的決策點

- tags 中文 vs 英文(user 問過,還沒選)
- 開頭要不要 podcast 介紹段(user 範例有,別人版沒有)
- 引述用 `>` blockquote vs「」嵌入式(user 範例只用 `>`,但 humanize 一致性上混用也可)
- 小節標題的「問題 + 結論」vs「純描述」結構

這幾項保持彈性,user 給明確指令再收斂。

## 不要做

- **不要對標任何人**(user 給的、別人版、之前的自己版):user 2026-08-09 明確說「你不用硬要學它,它不是標竿」
- **不要在 output 還沒穩定前催 cron**:user 2026-08-09 說「再你宅沒有穩定輸出之前,我不會讓你 cron」。多集都對齊 user-style 之前不主動建排程
- **不要寫完就長篇檢討**:user 2026-08-09 暗示他不要「我現在重新評分」這種長回應,直接做對比較重要

## 覆蓋(防止偷懶)

> 2026-08-10 user 發現 humanized 偏短(5,531 中文字 / 1.5-2 小時 podcast),懷疑 agent 偷懶。問題不在內容選擇,是 workflow 沒有下限機制。
> 2026-08-22 改制:字數是覆蓋的代理指標,現在改用直接量測(行號錨點認領率),字數降為參考。

### 真正的把關點:錨點認領率

寫作關的每一段都掛逐字稿行號錨點,`scripts/audit_worklist.py` 直接算「逐字稿有幾行被認領」,並印出未認領區間。這是直接量測覆蓋,不是代理指標:

- 認領率 <50%、或有單一錨點涵蓋 >30 行(蓋全篇刷認領率) → exit 1 退件
- 未認領的連續區間逐處列出 → 盲審關三分類「該補/可捨棄」,捨棄的在 audit 記理由

**字數與小節數都不再當關卡。** 2026-08-15 先拿掉「小節數 ÷ segments ≥ 30%」(量的是分段習慣,還逼人拆碎小標湊數);2026-08-22 再把 CJK 字數降為參考,理由是它用英文字數回推時長,快嘴頻道會跳一級、中文來源直接失真,而且下限會誘發補水。

### 參考字數(不擋交付,只當偏短的警訊)

- 30 分鐘以下:3,000 字 / 30-60 分鐘:4,500 字 / 60-90 分鐘:6,500 字
- 90-120 分鐘:7,500 字 / 120-180 分鐘:9,000 字 / 180 分鐘以上:10,500 字

`scripts/check_user_coverage.py` 仍可跑來看數字,但 exit code 不影響交付。差很多時回頭看認領率與未認領區間,**不要為了湊字數補水**。

### Segments 對應率(防「整段跳過」)

規劃表逐段標「寫/精簡寫/不寫」,寫或精簡寫至少 80%,**不允許把反方例證、機制細節、講者反駁的具體邏輯以「邊枝」為由跳過**。廣告與寒暄標「不寫」不算數。

「判不出是誰說的不是丟掉內容的理由;歸屬的保守只該降級指名,不該降級覆蓋」這條來自 skill,但在 user-style 裡要特別加重 — 2026-08-09 我自己跳掉的 11 段中,有 3-4 段屬於實質內容(Brad 的 ZIRP 反思、David 的 ZIRP vs AI 時代比較、Airtable 清算優先權條款),不是廣告/寒暄。

### Apply when

每集 `/yt` + `/humanizer-zh` 都跑。規劃表是關 1 的第一件事,`audit_worklist.py` 在關 1 交件後與關 2 改完後各跑一次。
